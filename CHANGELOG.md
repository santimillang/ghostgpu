# Changelog

All notable changes to this project are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

While ghostgpu is pre-1.0, breaking changes may occur in minor releases. The `ghostgpu.dev/v1alpha1` API carries no compatibility guarantee.

## [Unreleased]

### Added

- **Prebuilt CLI binaries.** The quickstart told people to install the operator from a release URL and then build the CLI from source, which cannot be followed without a clone — so every release now attaches five archives (`darwin`/`linux`/`windows` across `amd64`/`arm64`, minus `windows/arm64`, which nobody runs a Kubernetes test harness on) built with GoReleaser. `up`, `status`, and `capture` are plain API-server clients, so the CLI carries none of the Linux dependency the operator does. Archive filenames deliberately omit the version — `ghostgpu_linux_amd64.tar.gz`, not `ghostgpu_0.1.0_linux_amd64.tar.gz` — because GitHub's stable "latest" endpoint is `releases/latest/download/<exact filename>`, and a version-embedded name would have no stable URL at all: it would change on every release and break any `curl` one-liner committed to the README or a user's CI script.
- **`ghostgpu version`.** A downloaded binary could not previously say what it was built from, which is the first thing any bug report needs and the first thing worth running after unpacking an archive. GoReleaser's default ldflags populate the version, commit, and date at build time; an unset field is printed as its own name rather than left blank, because an empty version string reads like a release that forgot to identify itself.
- **A Helm chart.** Platform teams compose their test clusters out of charts, so a project installed only by a raw manifest URL was the odd one out. The chart is generated from the same kustomize overlay that produces `install.yaml` rather than hand-written a second time, because two hand-maintained copies of the same Deployment and RBAC diverge silently — a CI check now fails the build if the two drift. CRDs ship in the chart's `crds/` directory rather than `templates/`, because Helm resolves every release's resource kinds before creating anything, so a `GPUPool` declared in values alongside its own CRD would fail on first install; the tradeoff is that Helm never updates `crds/` on `helm upgrade`, which the chart's own README now calls out with a working upgrade command rather than leaving it to be discovered. `values.gpuModels`/`values.gpuPools` pass straight through to the CRs with no chart-side validation, because the CRD's OpenAPI schema is already the validator and a second copy of it in `values.schema.json` would just be another schema to keep in sync. Published both as an OCI chart on ghcr, alongside the image it deploys, and as a classic `helm repo add` index on GitHub Pages, because a fair share of tooling and of people still reach for that path and being absent from it is a needless complaint. The chart version is the release tag with its leading `v` stripped (`v0.1.0` → `0.1.0`) — verified against a real local OCI registry that `helm install --version v0.1.0` fails `FetchReference` while `--version 0.1.0` succeeds, because the pushed artifact is tagged with the stripped form.
- **Signed and attested release images.** A platform team that runs admission policy asks for image provenance before it asks about features, and keyless `cosign` signing costs a CI step and no key to manage or leak. The signature targets the image digest rather than the tag, because a signature over a mutable reference proves nothing once the tag moves, and the release workflow verifies the signature it just produced — an unverified signing story is a claim, not a control. Build provenance is attested for both the image and the CLI archives.
- **Per-workload utilization.** `spec.utilization.workloads` overrides the pool's readings for GPUs held by pods matching a label selector, so a simulated fleet can hold a job at 90% beside one at 4%. This is the fixture idle-GPU reclamation and utilization-based preemption actually need: those tools exist to work out *which* job is wasting its GPU, and until now every allocated card in a pool reported the same number, so the question could not be asked. Entries are first-match-wins and layer over `whenAllocated`, so one only has to state what makes that workload different.
- Research into the wider "behavioural workload simulation" roadmap item found that the scenarios people test have long windows — `avg_over_time(DCGM_FI_DEV_GPU_UTIL[24h]) < 10`, or under 20% for 30 minutes — which Prometheus computes from its own history and ghostgpu cannot backfill. Per-workload heterogeneity delivers the testable half with no time axis; the phase timeline is deliberately deferred rather than built on that assumption. See `docs/design/2026-07-31-behavioral-simulation-research.md`.
- **GPU fault injection.** `GPUPool.spec.faults` declares failed hardware, which is the hardest scenario to test for because it cannot be arranged on demand — there is no way to ask a production GPU to fall off the bus to see whether remediation drains the node. `Evict` models device loss and uncorrectable ECC: the workload running on that GPU is thrown off and its `ResourceClaim` released, so it can be rescheduled onto healthy hardware. `Unschedulable` models a card that still runs but must take no new work, such as one with a row remap pending a reboot.
- The mechanism was chosen from a spike rather than from documentation. A `NoExecute` DRA device taint was verified to evict a running workload and clear its claim allocation, with a negative control confirming an identical untainted pod survives the same wait — the first run of that spike used an invalid CEL field, produced a pod stuck `Pending` for an unrelated reason, and proved nothing, which is why the rerun asserts its control and aborts rather than printing a verdict either way.
- `spec.faults[].xid` surfaces on `DCGM_FI_DEV_XID_ERRORS`, the signal most GPU remediation actually watches, and rides on the device taint value so a `ResourceSlice` alone explains why a device is out of service. Faults and occupancy are independent declarations applied lowest-index-first with faults winning where they overlap, so "three busy, one faulted" means the failure happened to a GPU that was working. `ghostgpu status` reports faulted as a third state distinct from occupied and allocated.
- **DCGM-shaped metrics.** The operator serves simulated GPU telemetry on port 9400, dcgm-exporter's conventional port, so an existing scrape config or ServiceMonitor finds it without being rewritten. Metric and label names are taken from dcgm-exporter's default counter set rather than from memory, and pinned by a test, because dashboards and KEDA queries hardcode them exactly as tooling hardcodes the GFD labels.
- Metrics are attributed to the pod holding each GPU — `namespace`, `pod`, `container`, and under MIG `GPU_I_ID` and `GPU_I_PROFILE`. This is where the DRA-first decision pays off: the scheduler already recorded exact device identity in `ResourceClaim.status`, so there is nothing to re-derive from a container runtime and nothing to get wrong under MIG. An idle device carries no workload labels at all, rather than empty ones, because an empty `pod` label is a distinct series that `sum by (pod)` would happily group on.
- `GPUPool.spec.utilization` declares what a GPU reports when busy and when idle, rather than randomising it. A metric that jitters cannot be asserted against, and these numbers exist to drive a rule under test — "scale down when utilization stays below 20% for ten minutes" is only testable if the fleet reliably does that. Framebuffer used and free are derived from the GPU's own memory, so they always sum to it.
- Power and temperature are emitted only when declared. ghostgpu has no thermal or power model, and a plausible-looking wattage would be fabrication rather than simulation. Under MIG they stay at card level, matching dcgm-exporter: instances share one piece of silicon, so a per-instance wattage is a number no hardware could produce.
- **Pre-existing occupancy.** `GPUPool.spec.occupancy` declares how full a fleet starts, so fragmentation scenarios exist before any workload is submitted — *seven GPUs free but spread 2/2/2/1 across four nodes; does a four-GPU job schedule?* Building that with filler pods is racy and, more importantly, not reproducible: where the filler lands is the scheduler's choice, so the scenario under test is never quite the one intended. Entries are first-match-wins so a fleet can be unevenly full, and `ghostgpu up --busy-per-node N` covers the even case.
- Occupancy is expressed as a DRA device taint on the ResourceSlice ghostgpu already publishes, and as `allocatable` below `capacity` on the legacy path. Both were verified against a live scheduler with negative controls before the design was chosen: a claim is refused when only occupied devices remain, and the *same* pending claim is placed the moment the occupancy is lifted. ghostgpu never writes `ResourceClaim.status`. A spike confirmed it could — nothing in the API server prevents it — which is what makes refusing a commitment rather than a constraint: forging allocation would make the simulation lie to the component under test.
- Under `sharingMode: mig`, `busyPerNode` counts whole cards and every instance carved from an occupied one is tainted. Not a simplification: MIG instances draw on shared counters, so leaving a single profile allocatable would mean the card was never occupied. Partial-instance occupancy is deliberately out of scope.
- `ghostgpu status` reports occupied separately from allocated, and subtracts both from free. They are different states with different owners, and a device declared busy reports `(declared)` rather than naming a pod that does not exist.
- **`ghostgpu capture`.** Reads a cluster that already has GPUs and prints the `GPUModel`/`GPUPool` manifests reproducing it, so a fleet no longer has to be described by hand — which is guesswork about exactly the details that differ from the defaults and cause the bug being chased. Product, memory, and compute capability come from GFD labels; the per-GPU MIG layout from `nvidia.com/mig-*` capacity; NVLink domains and NUMA locality from `ResourceSlice` attributes, which no node label carries. Distinct node shapes become distinct pools, and the kwok `Node` manifests are emitted alongside them, so applying the output is enough to have the fleet.
- Capture is strictly read-only against the source cluster, enforced by the type it holds rather than by its call sites: the client is narrowed to a wrapper with no create, update, or delete to reach. This is the inverse of the safety invariant — pointing a simulator at production has to be provably harmless — and the e2e suite checks it against a live API server by asserting resourceVersions are unchanged. Output goes to stdout, so applying it stays the user's own explicit act, and node names are synthesised rather than copied because captured output is meant to be shareable.
- Capture is lossy by design and says so. A non-uniform MIG layout, incomplete GFD labels, the `single` MIG strategy, and MIG on a node whose physical GPU count nothing in the cluster reveals are all reported on stderr, leaving `> fleet.yaml` a clean file. MIG profiles for hardware ghostgpu has no table for are derived from the profile names themselves, which encode the slice count and framebuffer — a reading asserted against every built-in table rather than assumed.
- **MIG partitioning.** `GPUPool.spec.sharingMode: mig` divides each simulated GPU into MIG instances published as DRA partitionable devices, so overlapping profiles on one physical card are mutually exclusive — enforced by the upstream scheduler through shared counters, with no allocation logic in ghostgpu. Profiles come from built-in tables for the A100 (40GB and 80GB) and H100, or from `spec.migProfiles` for hardware ghostgpu does not recognise.
- Sharded ResourceSlice publication. Two measured API limits force the layout — at most 8 `sharedCounters` and 64 counter-consuming devices per slice — so a node becomes `ceil(gpus/8)` counter slices plus `ceil(gpus × profiles/64)` device slices in one DRA pool. Counter sets resolve pool-wide, so a GPU's profiles may straddle a slice boundary.
- Mixed-strategy node advertisement under MIG: one extended resource per profile (`nvidia.com/mig-1g.10gb`), `nvidia.com/gpu` at zero, and the `nvidia.com/mig.capable` / `nvidia.com/mig.strategy` labels. Per-profile counts are derived from both the compute-slice and memory budgets, matching NVIDIA's published instance counts.
- `ghostgpu status` reports which devices are published and which pod holds each one, with `--node` to narrow to one node and `--budgets` to show how much of each physical GPU's compute-slice and memory budget is already consumed — the answer to why another MIG instance will not fit. Everything is derived from `ResourceSlice`s and `ResourceClaim`s already in the cluster; no allocation state is stored.
- `GPUPool.spec.migPartition` declares which MIG instances actually exist on each GPU, modelling *static* MIG (instances pre-created by an administrator) alongside the *dynamic* MIG that an empty partition models. With a partition declared the extended-resource counts sum to something the hardware can genuinely satisfy, so a scheduler cannot overcommit the node. A partition that cannot fit one GPU is rejected with `MIGPartitionInvalid` and nothing is published.
- `ghostgpu up --sharing-mode mig [--mig-profiles 1g.10gb,3g.40gb] [--mig-partition 3g.40gb=1,1g.10gb=4]`.
- `GPUModel` and `GPUPool` cluster-scoped CRDs describing simulated GPU hardware and how it is advertised (DRA `ResourceSlice`s and/or legacy `nvidia.com/gpu` extended resources).
- `GPUPool` controller. For every kwok-managed node matching a pool's selector it publishes a DRA `ResourceSlice`, patches `nvidia.com/gpu` capacity and allocatable, applies GPU Feature Discovery labels, and reports matched nodes and published devices on `status`. Slices belonging to departed nodes are pruned.
- GPU Feature Discovery-compatible node labels (`nvidia.com/gpu.present`, `.count`, `.product`, `.memory`, `.compute.major`, `.compute.minor`), matching NVIDIA GFD key names and value formats so existing tooling selects on simulated nodes unchanged.
- `ghostgpu up` CLI, turning a handful of flags into the `GPUModel`/`GPUPool` pair so that adoption does not require hand-writing custom resources. Re-running applies changes rather than failing on AlreadyExists, `--dry-run` renders manifests without contacting a cluster, and the command reports how many devices the operator published once it has observed the new spec.
- End-to-end suite asserting real kube-scheduler behaviour against simulated hardware: extended-resource placement and refusal to overcommit, DRA allocation honouring an NVLink topology selector, GFD labels, published `ResourceSlice`s, pool status, and the safety invariant. The e2e cluster is now kwok on kind with `DynamicResourceAllocation` enabled, because a plain kind cluster can host the manager but cannot exercise anything it does.
- Project scaffolding: kubebuilder v4.15.0, Apache-2.0 license, CI for build, lint, unit/envtest, and e2e.
- Community health documentation: contributing guide, code of conduct, security policy with threat model, and governance.

### Changed

- API group corrected from `ghostgpu.ghostgpu.dev` to `ghostgpu.dev`. kubebuilder composes the group as `<group>.<domain>`, which doubled the name. Safe to change while unreleased; it would be breaking afterward.
- `spec.advertise.dra` and `spec.advertise.extendedResource` are now `*bool` rather than `bool`. A defaulted boolean with `omitempty` serializes an explicit `false` as absent, which the API server defaults straight back to `true`, making either path impossible to disable from a Go client.

### Known limitations

- Under MIG **without a declared `spec.migPartition`**, the legacy extended-resource path can be overcommitted. Scalar resources cannot express that profiles on one GPU are mutually exclusive, so a node advertising both `nvidia.com/mig-1g.10gb` and `nvidia.com/mig-7g.80gb` will let a scheduler allocate from both at once. Each count is faithful alone; their sum is not. This is inherent to modelling *dynamic* MIG, which the DRA path expresses correctly through shared counters. Declaring a partition models *static* MIG instead and makes the projection exact.

### Fixed

- A `GPUPool` manifest that omitted `spec.advertise` entirely advertised nothing. The nested fields carried defaults but their parent object did not, so the API server had no object to default into and both paths resolved to `false`. `spec.advertise` now defaults to `{}`.
