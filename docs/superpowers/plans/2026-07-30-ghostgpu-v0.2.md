# ghostgpu v0.2 Implementation Plan — MIG

**Goal:** expand a `GPUPool` into MIG profiles as DRA partitionable devices, so
that overlapping profiles on one physical GPU are mutually exclusive and the
upstream scheduler enforces it. This is the project's strongest confirmed
differentiator: `fake-gpu-operator` has no MIG-instance state at all.

**Evidence base:** `docs/superpowers/specs/2026-07-30-mig-sharding-findings.md`.
Do not re-derive the sharding strategy — it is measured, including negative
controls.

## Global constraints

Everything from the v0.1 plan still applies (WSL2 working copy, DCO sign-off,
never touch a node without the kwok annotation, fix lint rather than suppress
it, commits are gated on the user's approval). Additionally:

- **8 `sharedCounters` per slice. 64 counter-consuming devices per slice.** Both
  measured, both hard API limits. The 128-device figure from v0.1 applies only
  to devices without counters and is irrelevant here.
- **Counter sets resolve pool-wide**, so a GPU's profiles may span device slices
  and a pool may hold several counter slices.
- **Slice construction stays a pure function of its inputs.** A restarted
  operator must republish byte-identical slices, so shard assignment must be
  deterministic — no map iteration order, no time, no randomness.
- **Extended resources under MIG use NVIDIA's `mixed` strategy** (decided
  2026-07-30): one resource per profile, `nvidia.com/mig-1g.10gb: N`.

## Sharding strategy (settled)

```
counterSlices      = ceil(gpusPerNode / 8)
deviceSlices       = ceil(gpusPerNode * len(profiles) / 64)
resourceSliceCount = counterSlices + deviceSlices
```

### Task 1: MIG profile tables and the GPUModel API

**Files:** `api/v1alpha1/gpumodel_types.go`, `internal/mig/profiles.go` (+ tests)

Spec §5 places "MIG profile→GI-ID tables" in the **faithful** fidelity tier, so
built-in tables for known products are part of the contract rather than a
convenience. Users override only for hardware ghostgpu does not know.

- `MIGProfileSpec{Name string, Memory resource.Quantity, Slices int32}`
- `GPUModelSpec.MIGProfiles []MIGProfileSpec` (optional; empty means look up the
  built-in table by `productName`)
- `GPUModelSpec.MIGBudget *MIGBudgetSpec{Memory, Slices}` (optional; defaults to
  the model's own memory and the built-in slice count)
- `internal/mig.ProfilesFor(productName) ([]MIGProfileSpec, bool)` with real
  H100 and A100 tables

Validation that must be tested: a profile consuming more than the budget is
rejected; duplicate profile names are rejected; a profile name that is not a
valid Kubernetes label value is rejected, because it becomes part of a resource
name under the mixed strategy.

### Task 2: GPUPool sharing mode

**Files:** `api/v1alpha1/gpupool_types.go`, envtest specs

- `GPUPoolSpec.SharingMode string` — `none` (default) | `mig`. `timeSlicing` is
  v0.3 and must be rejected now rather than silently accepted.
- Reject `sharingMode: mig` when the resolved model has no profiles.

Guard against the v0.1 defaulting bug: assert the default via an **unstructured**
create, not the typed client, which always serializes the field.

### Task 3: Profile expansion and device identity

**Files:** `internal/mig/expand.go` (+ tests)

Pure functions, no client:

- `DeviceName(gpuIndex int32, profile string) string` → `gpu-0-1g-10gb`
  (profile dots become dashes; the name must be a valid DNS label)
- `CounterSetName(gpuIndex int32) string` → `gpu-0`
- `InstanceID(gpuIndex int32, profile string, ordinal int32) int32` — the
  `GPU_I_ID` a real driver would assign; v0.3's exporter depends on it

### Task 4: Sharded slice construction

**Files:** `internal/gpu/migslices.go` (+ tests)

`BuildMIGSlices(pool, model, nodeName) []*resourcev1.ResourceSlice` returning
counter slices followed by device slices, all sharing one `pool.name` and a
correct `resourceSliceCount`.

Tests must cover the boundaries the findings measured, because these are exactly
the cases an 8-GPU development node never exercises:

- 8 GPUs × 7 profiles → 2 slices (1 counter + 1 device); no slice exceeds limits
- 16 GPUs × 7 profiles → 4 slices; **two counter slices**
- 128 GPUs × 7 profiles → 30 slices; every slice within 8 counters / 64 devices
- a GPU whose profiles straddle a device-slice boundary still names its counter
  set correctly
- byte-identical output across two invocations (determinism)

### Task 5: Controller integration

**Files:** `internal/controller/gpupool_controller.go` (+ tests)

- Publish MIG slices when `sharingMode: mig`, whole-GPU slices otherwise.
- **Prune across the mode switch.** Flipping `mig` → `none` must delete the
  now-orphaned slices; the existing `ghostgpu.dev/pool` label already scopes
  this, but multi-slice pools make stale objects much easier to leak.
- Status: add `MIGProfilesPublished` alongside `DevicesPublished`.
- The safety invariant test must be extended, not replaced.

### Task 6: Mixed-strategy node advertisement

**Files:** `internal/gpu/nodelabels.go`, controller (+ tests)

Under `sharingMode: mig`:

- capacity/allocatable gains `nvidia.com/mig-<profile>: <count>` per profile
- `nvidia.com/gpu` goes to **0** — under mixed strategy the whole GPU is not
  separately allocatable
- labels gain `nvidia.com/mig.capable: "true"` and `nvidia.com/mig.strategy: "mixed"`

Removing a previously advertised `nvidia.com/gpu` count needs an explicit test:
patching capacity down is easy to get wrong and leaves phantom capacity.

### Task 7: e2e — MIG exclusivity and sharding

**Files:** `test/e2e/ghostgpu_test.go`, `test/e2e/testdata/mig-*.yaml`

Reproduce the spike as regression tests against a deployed operator:

- a claim for `7g.80gb` blocks a `1g.10gb` claim on the same GPU; releasing it
  unblocks (the negative control, which is what proves counters are the cause)
- a **16-GPU pool** schedules correctly, exercising multi-counter-slice
  resolution end-to-end
- mixed-strategy capacity appears on the node

### Task 8: CLI support

**Files:** `internal/cli/up.go`, `cmd/ghostgpu/main.go` (+ tests)

- `--sharing-mode none|mig` and `--mig-profiles 1g.10gb,3g.40gb` (empty uses the
  built-in table for the product)
- `--dry-run` must render the MIG fields; validation stays client-side so errors
  surface without a cluster

### Task 9: `migPartition` — static MIG layouts

**Files:** `api/v1alpha1/gpupool_types.go`, `internal/mig/resolve.go`, `internal/gpu/{migresources,migslices}.go`, e2e (+ tests)

Added 2026-07-30 after Task 6 exposed a fidelity gap that documentation alone
cannot close.

ghostgpu currently models **dynamic** MIG: every profile is advertised at once
and the scheduler picks, which is what NVIDIA's DRA driver does. Real **static**
MIG pre-creates instances, and GFD advertises exactly those. Projecting the
dynamic model onto scalar extended resources produces a node advertising both
`mig-1g.10gb: 56` and `mig-7g.80gb: 8` — each faithful alone, but their sum
overcommits, because no real node can offer both.

The fix is not to invent exclusivity in scalars but to model the layout static
MIG has and ghostgpu lacks:

```yaml
spec:
  sharingMode: mig
  migPartition:            # optional; omit for today's dynamic behaviour
    - profile: 3g.40gb
      count: 2
    - profile: 1g.10gb
      count: 1
```

- Declared: extended resources become exactly faithful (no overcommit, because
  that is genuinely all that exists), and DRA publishes only those instances.
- Omitted: current dynamic behaviour, with the approximated-tier caveat.

Both are real hardware behaviours, so supporting both is correct rather than a
workaround. Validation must reject a partition exceeding the GPU's budget,
which `mig.Resolve` already knows how to check.

The e2e suite from Task 7 must cover both modes: a declared partition advertises
only its own profiles, and the sum of extended resources is satisfiable.

## Definition of done

- `make test`, `make lint`, `make test-e2e` green.
- A 16-GPU MIG pool works end-to-end, proving multi-counter-slice resolution.
- Overlapping profiles are mutually exclusive, with a passing negative control.
- The safety invariant still holds; unmanaged nodes remain untouched.
- README and CHANGELOG updated; MIG moved from "planned" to "working".

## Explicitly out of scope

Time-slicing (v0.3) · DCGM metrics including `GPU_I_ID` (v0.3) · behavioral
workload simulation (v0.4) · fault injection (v0.5) · dynamic MIG reconfiguration
at runtime, which real hardware requires draining the GPU for.
